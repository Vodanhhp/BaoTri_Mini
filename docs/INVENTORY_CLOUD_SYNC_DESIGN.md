  - `inventory.adjust`
  - `inventory.delete`

## 3. Cloud data model

### 3.1 `public.inventory_items`

One row per material item and organization.

| Field | Purpose |
|---|---|
| `id` | UUID generated by Local and preserved by Cloud |
| `organization_id` | Tenant boundary |
| `code` | User-entered material code; never generated by the equipment ID engine |
| `code_normalized` | Server-derived uppercase/trimmed/whitespace-normalized uniqueness key |
| `name`, `item_group`, `unit` | Main material description |
| `part_number`, `size` | Optional technical identification |
| `quantity` | Server-owned current balance, non-negative |
| `min_quantity` | Low-stock threshold |
| `location`, `supplier`, `unit_price` | Warehouse metadata |
| `created_by_user_id`, `created_by_label` | Creation attribution |
| `created_at`, `updated_at`, `archived_at` | Server timestamps and soft archive |

Constraints:
- Unique `(organization_id,id)` and `(organization_id,code_normalized)`.
- Quantity and minimum quantity must be non-negative.
- Item code and name must be non-blank.
- Quantity is never accepted in a metadata update payload.
- Server derives `code_normalized`; client-supplied normalized codes are ignored/rejected.

### 3.2 `public.inventory_movements`

Append-only stock ledger.

- Stable movement UUID generated by Local and preserved by Cloud.
- `organization_id`, `item_id`, movement date and type (`opening`, `in`, `out`, `adjustment`).
- Positive absolute `quantity`, signed `quantity_delta`, server-computed `balance_before` and `balance_after`.
- Optional `counted_quantity`, required reason, actor ID/label, optional `linked_asset_id`, and the originating `mutation_id`.
- Composite foreign key to `inventory_items(organization_id,id)`.
- Optional composite foreign key to `assets(organization_id,id)` for equipment linkage.
- Unique `(organization_id,mutation_id)` and unique movement identity within the organization.
- No update/delete endpoint. Direct client insert/update/delete is revoked. Historical movements are never hard-deleted by normal inventory operations.

Use a fixed numeric precision that matches Local validation; before enabling Cloud writes, Local validators and SQL numeric scale must be made identical. Do not silently round a stock quantity during sync.

### 3.3 Private operational tables

- `private.inventory_mutation_receipts`: idempotency receipt keyed by `(organization_id,mutation_id)`; stores actor, operation, exact request payload and result snapshots.
- `private.inventory_sync_counters`: one monotonically increasing sequence per organization.
- `private.inventory_sync_events`: immutable ordered events with `mutation_id`, event type (`item_upsert`, `item_archive`, or `movement_append`), item snapshot, optional movement snapshot, and server timestamp. The mutation ID lets a device recognize its own mutation after a lost RPC response.
- `private.inventory_activity_history`: append-only audit of metadata changes and archive actions; movement rows remain the authoritative quantity history.

All private tables enable RLS and revoke direct access from `public`, `anon`, and `authenticated`.

## 4. RPC contract

All privileged implementations live in `private`, use `SECURITY DEFINER`, `SET search_path = ''`, and `SET row_security = off`. Each implementation must explicitly check `auth.uid()`, active organization, and the relevant `private.has_org_permission` permission. Public RPC wrappers are `SECURITY INVOKER`, with execute granted only to `authenticated`; revoke execute from `PUBLIC` and `anon`.

### Create

`create_inventory_item(p_organization_id, p_item_id, p_mutation_id, p_item, p_opening_quantity, p_opening_movement)`

- Requires `inventory.create`.
- If opening quantity is greater than zero, also requires `inventory.adjust`.
- Preserves Local item and movement UUIDs and the user-entered code.
- Creates item, optional opening movement, receipt, audit record and feed event in one database transaction.
- Zero opening quantity creates no movement.
- Duplicate normalized code is rejected; Cloud never overwrites an existing item.

### Metadata update

`update_inventory_item_metadata(p_organization_id, p_item_id, p_mutation_id, p_expected_cloud_updated_at, p_payload)`

- Requires `inventory.update`.
- Strict allow-list: code, name, item_group, unit, part_number, size, min_quantity, location, supplier, unit_price.
- Rejects quantity, balance, movement, archive, organization and actor fields.
- A changed `min_quantity` additionally requires Admin role, checked server-side with `private.has_org_role(organization_id,'admin')`.
- Locks the item row and compares `updated_at` with the expected Cloud version. A mismatch is a conflict, never last-write-wins.

### Stock movement

`apply_inventory_movement(p_organization_id, p_item_id, p_mutation_id, p_expected_cloud_updated_at, p_movement)`

- Requires `inventory.adjust`.
- Supports stock-in, stock-out and physical count adjustment.
- Server locks the item row, computes all balances, rejects negative resulting stock and ignores client-supplied before/after balances.
- Count adjustment accepts the counted physical quantity; server computes the signed delta. Delta zero returns `no_change` and creates no movement, receipt or feed event.
- Item balance update, movement insert, receipt, audit and feed event commit atomically.
- Opening movement is only created by the Create RPC, not as a separate mutation.

### Archive

`archive_inventory_item(p_organization_id, p_item_id, p_mutation_id, p_expected_cloud_updated_at)`

- Requires `inventory.delete` and Admin role server-side.
- Only archives an item whose current balance is exactly zero.
- Does not delete movement rows or receipts.
- Uses optimistic Cloud timestamp and idempotency receipt.

### Incremental Pull

- `get_inventory_sync_checkpoint(p_organization_id)` returns the current per-organization sequence.
- `list_inventory_sync_changes(p_organization_id,p_after_sequence,p_limit)` returns ordered events, `has_more`, `next_cursor`, and server timestamp.
- Permission: `inventory.view`.
- Page size is bounded (1–500); cursor must be non-negative and strictly monotonic.
- Event sequence allocation locks the organization's counter row until transaction commit. This prevents a later committed mutation from receiving a sequence lower than an earlier uncommitted mutation.
- The first Cloud rollout starts the Local cursor at sequence 0. There is no pre-existing Cloud Inventory dataset to bootstrap; every Cloud item is created through the checked Create RPC and therefore emits a feed event. Do not prune feed events until a separately designed snapshot/bootstrap protocol exists.

## 5. Idempotency and concurrency

- Every Local mutation UUID is stable across retries.
- Each private RPC acquires a transaction-scoped advisory lock for `organization_id:mutation_id`, checks the receipt first, and returns the prior result only if actor, target item and exact payload match.
- Reusing a mutation UUID with a different request is rejected.
- The item row is locked with `FOR UPDATE` before stock calculations or metadata writes.
- A Cloud timestamp mismatch returns a conflict snapshot; the client preserves Local and Cloud snapshots for manual resolution.
- Item mutations are processed sequentially per item, in Local creation order. After a mutation succeeds, the worker updates the Cloud link timestamp and uses that latest timestamp for the next queued mutation. It must not reuse the stale timestamp copied into all queued records at Local-write time.
- If one mutation conflicts, later mutations for that item remain pending and are not sent.
- Never use device clocks as the conflict authority.

## 6. Local ↔ Cloud worker contract

The Cloud worker will be a separate module and will be called from the existing App sync cycle.

Push order per item:
1. `create` (including opening balance movement)
2. `update_metadata`
3. `post_movement` / `adjust_count`
4. `archive`

Worker requirements:
- Online, authenticated, active organization only; never sync `local-preview`.
- Re-check permissions from the active organization context before every push category; server re-checks permissions independently.
- Use existing `startSyncEngine` scheduler and `requestSync()` signal; no second timer.
- Retry the same mutation UUID after network timeout; do not generate a new UUID.
- Mark a mutation applied only after the RPC returns a valid receipt/result.
- A timeout after server commit is recovered by replaying the same mutation ID.
- Pull events validate organization, sequence, event type and snapshots before applying.
- Apply pulled item/movement/event/cursor updates in one Dexie transaction.
- If the item has pending Local mutations, do not overwrite it with a Cloud snapshot. Preserve both snapshots and mark conflict.
- Movement IDs and mutation IDs are deduplicated; movement history remains append-only.
- Viewer may pull but cannot push. Technician can create/update/adjust but cannot archive. Admin can perform all supported operations.

## 7. Data API and function security

Supabase's current Data API guidance distinguishes object grants from RLS policies. The design intentionally grants no direct table access to browser roles and exposes only the authenticated public RPC wrappers. RLS is still enabled on all public tables as defense in depth. Public wrappers must be SECURITY INVOKER; privileged implementation functions stay in the private schema with explicit authorization and tightly scoped grants.

The current Supabase changelog also records the staged change to default Data API exposure for new tables. The migration must not rely on implicit grants or automatic exposure. Confirm the target project's Data API settings at implementation/release time.

## 10. Cloud client implementation checkpoint (24/11/2026)

Client-side Cloud protocol code is now present on the feature branch:

- `src/lib/inventoryCloud.ts` implements the agreed RPC client contract for create, metadata update, movement, archive and incremental pull.
- Pending mutations are grouped and sent sequentially per item in Local creation order. Each mutation reads the latest `InventoryCloudLink.cloudUpdatedAt`; the stale expected timestamp captured at Local write time is not reused.
- A conflict blocks later mutations for that item. Existing conflict records are included in queue inspection.
- RPC results are validated before marking a mutation applied. Network failures retry with the same mutation UUID; recognized authorization/version/identity conflicts are held for manual resolution.
- Pull validates tenant, event type, event sequence, page size and next cursor. Item, movement, mutation/link state and cursor are applied through Dexie transactions.
- Remote events do not overwrite pending Local state; the Cloud snapshot is retained in `InventoryCloudLink.conflictSnapshot`.
- Append-only movement records are deduplicated by stable movement ID and mutation ID.
- Local inventory writes call the existing shared `requestSync()` scheduler. The existing App sync cycle now understands `inventory.view` separately from `assets.view`, and the inventory panel refreshes after pull events.
- The App feature gate `INVENTORY_CLOUD_SYNC_ENABLED` is deliberately `false`. The client code is dormant until the SQL migration is reviewed, approved, applied and verified. The UI continues to state that Inventory is Local-only.
